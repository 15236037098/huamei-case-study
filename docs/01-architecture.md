# 01 · 架构：把对话拆成可替换的五层

> 目标不是画得漂亮，而是每一层都能单独降级、单独测试。

## 分层

```
触达层    Web 获客顾问 · 管理后台 · IM 渠道适配
接入层    Node 网关 · 鉴权 · SSE · 并发与超时
智能层    意图识别 · LangGraph 编排 · 回答策略 · 风险门禁
知识层    知识发布 · 运行时索引 · GraphRAG / 本地检索
数据层    SQLite / PostgreSQL · Redis · OSS · 审计与观测
```

### 触达层

- **获客顾问**是独立的 Vite 应用，只依赖 HTTP 接口，不直接持有模型或数据库客户端。这样它可以独立部署、独立回滚，也方便做移动端适配。
- **管理后台**和服务端同源部署，走管理会话 + 五岗位权限。菜单位置、接口许可、数据范围是三层判断，不是只在前端隐藏按钮。
- **渠道适配**是显式的：企业微信、抖音、小红书在完成官方凭证、回调验签和发送验收之前，只允许登记已经发生的人工沟通，不把草稿标记为"已发送"。

### 接入层

网关按职责拆成 public / admin / knowledge / local 四组路由，共享一份请求上下文（租户、身份、请求 ID、限流键）。几个刻意的边界：

- **超时覆盖到响应体**：只给响应头设超时，上游卡在正文时请求会长时间挂起。这里把超时保持到读完响应体，半开响应按配置失败。
- **出站地址先校验再发凭证**：调用外部服务（如 GraphRAG）前先校验目标地址，非法地址不发起请求，直接走降级。
- **响应体有上限**：模型返回按块读取，超过上限立即中止，避免异常网关把整段超大 JSON 读进内存。

### 智能层

智能层不是一个巨大的 `agent` 函数，而是四个可以分别测试的策略模块：

| 模块 | 职责 | 判定失败时的行为 |
| --- | --- | --- |
| 意图识别 | 当前轮意图、实体、对话动作、澄清判断 | 退回规则结果 |
| 任务推进 | 子任务、槽位、下一步动作 | 只追问一个缺口 |
| 回答策略 | 用哪条证据路线、能否独立作答 | 转人工或明确说不知道 |
| 风险门禁 | 医疗异常、隐私、越权 | 先接管，不检索 |

### 知识层

知识有三态：**原始素材 → 内部草稿 → 正式发布**。对客回答只读"发布快照"，运行时不直接扫原始素材。检索有三条路径，按可用性依次回退：

1. GraphRAG（图谱 + 向量）——需要索引版本就绪；
2. 本地审核知识检索——默认路径；
3. 无命中——追问或转人工。

回退是**可解释**的：接口会返回检索来源和降级原因，后台能看到"这次为什么没走图谱"。

### 数据层

- 本地开发用 SQLite（WAL），生产用 PostgreSQL（行级安全 + 五角色）；两者共享同一份仓储接口，业务代码不感知后端。
- Redis 是可选的：不可用时回退进程内缓存，不影响正确性，只影响命中率。
- 文件走对象存储，边下边写、累计计数、超限中止并清理半成品。

## 一次咨询的路径

```
用户输入
  → 安全门禁（不通过：接管 / 阻断，不检索）
  → 意图识别（规则候选 + 模型提议 + 程序校验）
  → 任务推进（子任务、槽位、是否缺信息）
  → 证据检索（发布快照 → GraphRAG / 本地检索）
  → 本地草稿（带引用）
  → 模型润色（脱敏上下文，仅润色）
  → 输出合规检查
  → 分段流式下发 + 落库归档
```

关键点：**任何一步失败都不允许"编一段"**。缺证据就追问，缺权限就转人工，缺服务就降级并告诉后台。

## 为什么这么分

早期版本把识别、检索、生成写在一个大文件里，结果是：改一句话术要跑全量回归，模型换了要改业务分支，出问题只能看日志猜。拆成策略模块之后：

- 新增一个意图 = 一条规则数据，不是一段新分支；
- 换模型 = 换 `invokeStructured` 的实现，契约不变；
- 降级 = 每一层都有明确的 fallback，而不是整体的 try/catch。

代价是模块变多、调用链变长。所以每个模块都有契约测试，接口变化必须同时改测试，否则 CI 直接失败。
