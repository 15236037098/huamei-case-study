# 05 · 工程化：能被验证的部分

> 一个人说"我做完了"不算数，测试说才算。

## 测试是分层的

192 条用例按依赖程度分层，跑不同层解决不同问题：

| 层 | 数量 | 干什么 | 依赖 |
| --- | --- | --- | --- |
| unit | 121 | 纯逻辑：意图、策略、解析、权限判断 | 无 |
| integration | 30 | 进程内链路：路由、会话、服务契约 | 本地文件 |
| postgres | 26 | 真实数据库：迁移、RLS、五角色、加密字段 | 隔离库 + 隔离角色 |
| browser | 12 | 真实浏览器：管理后台交互、移动端、XSS 边界 | Chrome |
| live | 3 | 真模型、真外部服务 | 凭据与网络 |

默认套件只跑其中 88 条，覆盖核心链路；全量在交付前跑。

分层的好处是**反馈速度**：改一句意图规则跑 unit，几秒出结果；改数据库迁移才需要起 PostgreSQL。

所有用例在 `tests/manifest.mjs` 里登记分类，CI 按类别调度，而不是靠文件名猜。

## 数据库测试必须隔离

跑在开发库上是最常见的坏习惯：跑一半失败，留下一堆脏数据，下次跑结果不可信。这里的做法：

- 每个用例组创建临时数据库和临时角色；
- 用例结束（包括失败）清理数据库与角色；
- 迁移在隔离库里从头执行一遍，验证的不是"当前库能用"，而是"空库能起来"。

最后一条抓过真实问题：本地库因为跑过很多次迁移，掩盖了一条新迁移在空库上失败的缺陷。

## 安全不是最后加的一层

| 项目 | 做法 |
| --- | --- |
| 越权 | 菜单、接口、数据三层判断，接口层不信任前端 |
| 注入 | 参数化查询，仓储层统一构造 |
| XSS | 所有渲染走 `escapeHtml`，全局搜索不拼 `innerHTML` |
| 联系方式 | 一次性查看 + 审计，查看即记录 |
| 密钥 | 启动时校验，不落日志，不进 Git |
| 红队 | 64 条用例，覆盖提示注入、越权、泄露、路径穿越 |

红队用例是持续跑的，不是上线前跑一次。改完安全相关代码，`npm run test:security:redteam` 是提交前的最低要求。

## 性能：先测再改

| 指标 | 改前 | 改后 | 手段 |
| --- | --- | --- | --- |
| 客户快照（501 客户） | 1.14MB 响应 | gzip 后 11KB | JSON gzip |
| 快照响应时间 | 约 84ms | 27–32ms | 预建索引 + 1 秒同主体复用 + 变更指纹 |
| 模型响应体 | 无上限 | 4MB 中止 | 按块读取 + 累计计数 |

快照这一项值得说明：最初的问题是 O(会话 × 客户) 的查找，每次请求都全量重建。改法是预建会话索引、同主体 1 秒内复用、只对关键字段算变更指纹。gzip 只是缓解，服务端分页才是根治——这条仍留在待办里。

## 提交与审查

一个典型批次的规模是 71 个文件、+2703 / -369。这种规模的提交如果不写清楚，三个月后没人敢动。所以每次交付都配一份变更说明，写四件事：

1. 改了什么、为什么；
2. 哪些是行为变更（部署必须重启）；
3. 验证了什么、用什么命令验证；
4. 还有什么没解决。

审查文档里会明确区分"已修复"和"已知限制"。比如"客户快照仍是全量返回"、"尚未添加 CSP"、"知识原件仍以 base64 写入 JSONB"都写在限制里，而不是假装不存在。

## 自动化检查清单

```bash
npm test                     # 默认套件
npm run test:security:redteam
npm run test:postgres:ci     # 隔离库集成
npm run ci:validate          # 校验 CI 工作流本身
npm run release:preflight    # 发布前门禁
```

`ci:validate` 这一条经常被忽略：CI 配置写错了比没有 CI 更糟——它会给你一个绿色的假象。

## 教训

- **先定边界再写功能**。意图白名单、证据路线、拒答规则如果后补，代码里会到处是特例。
- **降级路径要和主路径一起写**。事后补的降级，通常在真实故障里从来没被执行过。
- **性能问题先量化**。凭感觉优化，改完不知道有没有变好。
- **测试数量不是目标**。192 条里最有价值的是那几十条"曾经真的坏过"的回归用例。
