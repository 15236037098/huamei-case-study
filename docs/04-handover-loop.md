# 04 · 流式回答与人工接管闭环

> 对话体验的难点不在"答得快"，而在"人机切换的瞬间不出错"。

## 分段流式，而不是 token 级

前台看到回答逐段出现，但实现上不是 token 级流式：回答先由本地草稿或受控模型一次生成，再按段落切成 SSE 事件下发。

```text
event: segment   data: { index, text }      ← 逐段
event: final     data: { message, citations, structured_data }
```

这样做有三个好处：

1. **流式结果与归档结果同源**。最终事件携带完整回执，和普通 JSON 接口完全一致，后台不需要"再查一次数据库才知道用户看到了什么"。
2. **失败可重放**。生成阶段失败就整体失败，不会出现"前半段发出去了、后半段没了"的残缺状态。
3. **消息 ID 稳定**。同一轮用户消息对应同一个助手消息 ID，浏览器历史和持久化历史不会各算一份。

代价是首段延迟比 token 流略高。对售前场景来说，一段完整的、带引用的回答比逐字蹦出来更可信，这个取舍是刻意的。

## 会话恢复

刷新页面、切换设备、网络断开重连，都应该回到同一个会话。做法是：

- 服务端持有会话与消息，前端只保存会话标识；
- 重连时拉取"最后一条已确认消息之后"的增量，而不是全量重放；
- 前端对未确认消息做本地草稿标记，确认后合并，避免重复发送。

后台的实时同步还有一层退避：SSE 连续失败后关闭推送，退化为 15 秒定时同步。宁可慢一点，也不要无限重连把服务打满。

## 人工接管的关键是"原子"

接管不是一个按钮，而是一串必须要么全做、要么全不做的状态变更：

```
顾问点击接管
  → 服务端原子领取（同一时刻只有一个顾问能领到）
  → 会话进入"人工接待"，AI 停止对外发送
  → 顾问回复 → 消息写入统一会话记录并同步到前台
  → 记录跟进 / 完结 → 写工时与审计
  → 交回机器人
```

几个容易出事的点：

| 风险 | 处理 |
| --- | --- |
| 两个顾问同时领取 | 服务端原子领取，第二个返回已领取 |
| 接管后 AI 还在回答 | 接管状态是发送前置条件，不是展示状态 |
| 消息只到了后台没到前台 | 写入统一会话记录，前台轮询/推送同源 |
| 完结时工时丢失 | 完结与工时写同一次事务，失败即整体失败 |
| 排队久了旧任务消失 | 未关闭任务单独查询，与最近窗口合并去重 |

第五行是一条真实的线上隐患：交接单最初只捞最近 500 条，积压超过 500 之后，旧的 pending 任务会从顾问视图里消失——任务没丢，但没人能看到它。

## AI 在该停的时候必须停

"人工接管期间 AI 不抢答"不是靠提示词约束，而是靠状态机：会话处于人工接待时，AI 的回复通道直接关闭，连生成都不触发。这比"生成后再判断要不要发"可靠得多，也省了成本。

同时保留一条通道：人工接待期间客户问的技术性问题，AI 可以生成**建议回复**给顾问，但不自动发送。

## 我在这条链路上的位置

接管本身由负责客户与人工接待的同事实现，我负责的是**对话侧的状态衔接**：

- 前台如何感知"已被接管"并停止自动回复；
- 接管发生时正在流式下发的回答如何收尾；
- 交回机器人后，上下文如何续上而不是从零开始。

第三点最容易被忽略：交回机器人时如果只恢复"最近几条消息"，AI 会重复问已经问过的问题。所以接管期间的人工消息也要进摘要，并且标记来源是"人工"。

## 还没做好的

- 接管期间的 AI 建议回复目前是手动触发，没有做"高价值问题自动提示"；
- 会话摘要 500 字上限在长对话里会丢细节，需要分层摘要；
- 多设备同时在线时的未读计数是近似值，不是严格一致。
