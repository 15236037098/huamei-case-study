# 03 · 证据约束回答：先有资料，再有措辞

> 大模型最危险的能力是"把没有的东西说得很像有"。

## 每个意图绑定一条证据路线

| 意图族 | 证据 | 不许做什么 |
| --- | --- | --- |
| 项目介绍 / 比较 / 按关注点发现 | 已审核的项目知识 | 不承诺效果、不替客户判断适不适合 |
| 医生介绍 / 比较 | 医生资料 | 不编造擅长领域和案例 |
| 医生排班 | 仅确认资料存在 | 不报班次，交人工实时核验 |
| 价格 | 项目价格目录 | 不报历史价，不给"大概多少钱" |
| 政策 / 权益 | 政策目录 | 不外推有效期和适用条件 |
| 预约 | 预约服务 | 聊天里的"同意"不登记，仍要走独立表单 |
| 受限资料 | 仅元数据 | 不展示案例、照片、沟通记录 |

没有对应证据时的正确行为是**追问一个关键问题**或**请人工核验**，不是找一段相似资料补上。

## 两步生成：本地草稿 + 模型润色

```
命中证据
  → 本地生成结构化草稿（要点、引用、边界声明）
  → 模型润色（只改措辞，不改事实）
  → 输出合规检查（价格承诺、绝对化用语、内部实现词）
  → 下发 + 归档
```

这么做的原因很实际：如果让模型直接"看着资料写回答"，它会在资料不足的地方补一句听起来很合理的过渡句，而这句过渡句往往就是承诺。

本地草稿负责**说哪些事实**，模型负责**怎么说人话**。模型拿到的上下文只有分类结果和脱敏字段，不含完整对话历史和客户资料——即使模型被提示注入，也拿不到它不该知道的数据。

## 引用不是装饰

回答末尾的引用（"项目价格：鼻部 · 需核验"）有三个作用：

1. 客户能看到这句话的依据是什么；
2. 后台能看到这次回答引用了哪个发布版本；
3. 知识撤稿时可以按引用回溯，定位受影响的会话。

引用与回答在同一次响应里生成、同一次落库，不存在"回答有了、引用后补"的窗口。

## 拒答与追问的边界

| 情况 | 行为 |
| --- | --- |
| 完全没命中知识 | 追问一个最关键的缺口，不用泛泛的科普顶替 |
| 命中了但只覆盖一部分 | 先答已覆盖的部分，明确说明剩下的需要核验 |
| 命中但版本已撤稿 | 不引用，转人工 |
| 涉及个体适用性 / 禁忌 | 不做判断，交医生面诊 |
| 涉及价格承诺 | 给核验口径，不给数字 |

"我不知道"在产品里是一个**正常路径**，不是异常。这一点如果不在产品设计阶段定下来，后面一定会被业务方用"转化率"逼着改回去。

## 联系信息：不交给模型

留手机号这件事完全走确定性规则：正则识别 → 校验格式 → 去重 → 写入联系方式库 → 告知客户后续处理方式。

不走模型的原因：模型可能改写号码、可能把"138"听成"去三八"、也可能在润色时把号码删掉。这种一步错就丢客户的操作，不该有任何概率成分。

## 效果如何衡量

- 每条回答是否带引用、引用是否属于已发布版本——可自动化断言；
- 是否出现价格承诺、绝对化用语、内部实现词——规则可查；
- 客户侧：追问率、留资率、转人工率——需要真实流量，目前只有本地评测集。

评测集里我把"应该拒答"的样本和"应该回答"的样本分开统计。只看回答准确率会掩盖一个问题：**过度拒答**同样让客户流失。

## 取舍

- 本地草稿的句式偏模板化，模型润色后好一些，但仍有痕迹。彻底解决需要更强的受控生成，成本更高；
- 引用粒度是"知识条目"，不是"句子级"，客户看不到具体是哪一句支撑了回答；
- 多知识源冲突时（价目表 vs 政策页）目前以发布优先级为准，没有做自动仲裁。
